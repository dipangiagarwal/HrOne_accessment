# REVIEW.md: Starter Code Defect Review

This document records the defects identified and resolved in the starter `app/main.py` implementation, along with aspects inspected and verified as correct.

## Confirmed Starter Defects and Fixes

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33–37) | Timezone unaware replacement and off-by-one grace calculation. 1) Blindly calling `punch_in.replace(hour=h, minute=m)` ignores IST (UTC+05:30) vs UTC; if punch_in is stored in UTC, replacing with (9, 30) yields 09:30 UTC. 2) Rule R2 specifies a punch-in is late only when strictly more than 10 minutes elapsed (> 600s). At 09:40:01 for a 09:30 shift, 601s elapsed. `int(601/60)` is 10. Checking `minutes > 10` returns False (10 is not > 10), incorrectly giving 0 late minutes. 3) Fails to handle overnight shifts where post-midnight punch-in belongs to the previous day's shift. | Punching in at 09:40:01 for a 09:30 shift returns 0 late minutes instead of 10. Punching in across an overnight shift anchors shift start to the wrong calendar date. | Converted punch-in to IST, anchored shift start to the attendance date in IST, checked `elapsed_seconds > 600`, and returned `int(elapsed_seconds // 60)` if late, else 0. |
| 2 | `compute_work_hours` (lines 40–41) | Uses Python's built-in `round()`, which applies banker's rounding (round half-to-even) instead of decimal half-up rounding (Rules R4 and R8). Also does not truncate instants to whole seconds (Rule R1). | 16,290 seconds (4.525 hours) produces `4.52` with `round()`, whereas half-up rounding requires `4.53`. | Truncated punch instants to whole seconds and used Python's `decimal.Decimal` with `ROUND_HALF_UP` to round to 2 decimal places. |
| 3 | `compute_overtime` (lines 44–48) | 1) Rule R3 specifies overtime applies only when elapsed minutes >= 30; otherwise 0. `max(0, minutes)` wrongly grants overtime for 5 or 15 minutes. 2) For overnight shifts (`shift_end <= shift_start`), `shift_end` falls on the next calendar day; the starter anchors it to `date_str`, computing ~16 hours of false overtime. 3) Subtracting naive `punch_out` from aware `end` raises `TypeError`. | Punching out 15 minutes after shift end returns 15 overtime minutes instead of 0. An overnight shift 22:00–06:00 punching out at 06:15 next day returns ~975 overtime minutes or crashes with `TypeError`. | Handled overnight shift day advancement (+1 day when `shift_end <= shift_start`), ensured both datetimes are timezone-aware IST, checked `elapsed_seconds >= 1800` (30 min), and returned `int(elapsed_seconds // 60)` if >= 30, else 0. |
| 4 | `health` (lines 72–74) | Returns HTTP 200 `{"status": "ok"}` unconditionally without verifying database connectivity. Contract requires 200 only if MongoDB answers a ping, otherwise 503. | Stopping MongoDB and calling `GET /health` returns 200 instead of HTTP 503. | Added `client.admin.command("ping")` inside a try-except block, raising `HTTPException(503)` if MongoDB is unreachable. |
| 5 | `create_employee` (lines 77–85) | 1) Check-then-insert race condition: `find_one` check followed by `insert_one` allows concurrent requests to create duplicates or trigger unhandled 500 errors. 2) No unique index created on startup. 3) Fails to validate `shift_start != shift_end` (422). 4) Returns `created_at` as a Python datetime rather than integer epoch milliseconds. | Sending simultaneous POST requests with identical `emp_code` results in duplicates or 500 errors. Creating an employee with `shift_start == "09:30"` and `shift_end == "09:30"` returns 201 instead of 422. | Created a unique index on `employees.emp_code` at startup, caught `DuplicateKeyError` to return 409, validated `shift_start != shift_end` with 422, and formatted `created_at` as epoch milliseconds. |
| 6 | `list_employees` (lines 88–96) | 1) Off-by-one pagination bug: `skip = page * page_size`. For page 1, `skip = 1 * 20 = 20`, completely skipping the first page of employees! 2) `total = db.employees.count_documents({})` counts the whole collection regardless of the department filter, violating Rule R10. 3) Missing sort by `emp_code` ascending. 4) Unvalidated `page` (< 1) and `page_size` (> 100). | `GET /employees?page=1` returns employees 21–40. Filtering by department returns `total` equal to total company count rather than department count. | Changed skip calculation to `(page - 1) * page_size`, passed the filter query to `count_documents(query)`, added `.sort("emp_code", ASCENDING)`, and added FastAPI parameter constraints (ge=1, le=100). |
| 7 | `punch_in` (lines 99–121) | 1) Missing 404 handling: if `emp_code` does not exist, `emp` is None, and accessing `emp["shift_start"]` raises `TypeError` (HTTP 500). 2) Timezone/date bug: uses local server time `datetime.fromtimestamp(...)` instead of IST, and ignores overnight shift date derivation (R1). 3) Race condition: check-then-insert allows duplicate punches on the same date. 4) Schema violation: returns forbidden `"id": str(res.inserted_id)` and unformatted datetime objects. 5) Status validation missing: allows arbitrary invalid strings. | Punching in for a non-existent employee crashes with 500. Two concurrent punch-ins create duplicate records. Punching in with seconds or boolean timestamps succeeds instead of returning 422. | Added employee existence check with 404, created unique compound index on `attendance_logs(emp_code, date)` and caught `DuplicateKeyError` to return 409, derived IST attendance date per R1, enforced `PresenceStatus`, truncated to whole seconds, removed `id`, and converted timestamps to epoch milliseconds. |
| 8 | `list_attendance` (lines 124–150) | 1) Critical memory and performance defect: `docs = list(db.attendance_logs.find(q))` loads all documents (~100,000) into Python memory and sorts in Python. 2) Incomplete sort: sorts only by `date` descending, omitting `emp_code` ascending. 3) Missing date validation: does not validate `date_from <= date_to` (422). 4) Schema violation: returns forbidden `"id"`, unformatted datetimes, and fails to handle legacy records missing `half_day` or `history`. | Calling `GET /attendance` with 100,000 documents consumes hundreds of megabytes of memory and takes seconds. Calling with `date_from=2026-07-10&date_to=2026-07-01` returns 200 with empty list instead of 422. | Pushed pagination and compound sorting `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)` down to MongoDB backed by index, validated `date_from <= date_to` with 422, stripped `_id`, provided legacy defaults, and formatted timestamps as epoch milliseconds. |
| 9 | `PunchInIn` / Timestamp validation (lines 63–67) | `punched_at` typed as `Optional[int]`. Pydantic coerces booleans (since `bool` is a subclass of `int`), floats (e.g. `1783312500000.5`), strings, and timestamps expressed in seconds (e.g. `1783312500`), all of which violate the contract requiring strict integer epoch milliseconds. | Sending `{"emp_code": "EMP0001", "punched_at": true}` or `{"emp_code": "EMP0001", "punched_at": 1783312500}` is accepted instead of rejected with HTTP 422. | Implemented custom validator `validate_epoch_milliseconds` that explicitly rejects booleans, floats, strings, and integers outside the valid range `[100000000000, 4102444800000]`. |
| 10 | Database Indexing & Startup (entire file) | The starter code creates zero database indexes at application startup. No unique index on `emp_code`, no unique index on `(emp_code, date)`, and no indexes to support pagination, filtering, or analytics pipelines. | Database queries execute full collection scans (`COLLSCAN`), and concurrent requests easily create duplicate employees and attendance records. | Implemented FastAPI `lifespan` context manager that creates all required unique and compound indexes automatically and idempotently on startup. |

## Inspected Components Verified as Correct

1. **`IST = timezone(timedelta(hours=5, minutes=30))` (line 25):**
   - Verified: Exactly represents Indian Standard Time (UTC+05:30) as required by Rule R1.
2. **`load_dotenv()` (line 20):**
   - Verified: Safely loads local `.env` configuration without overriding active environment variables, ensuring containerized/grader environment variables take precedence.
3. **Module-level `MongoClient` instantiation (lines 22–23):**
   - Verified: PyMongo's `MongoClient` is thread-safe and manages an internal connection pool across requests. Keeping the client at module level avoids the high latency of reconnecting on every HTTP request.
